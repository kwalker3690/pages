! Why This Is Brittle

▶

5 useEffects in MediaDrawer.tsx that interact non-obviously

Each effect handles a separate concern, but they share closure state and trigger each other through Redux dispatches and state changes:

// Effect 1: Auto-close when selection changes
useEffect(() => {
  if (!isMediaSelected) toggleMediaDrawer({ isOpen: false })
}, [isMediaSelected]) // fires on ANY selection change

// Effect 2: Auto-focus first interactive element
useEffect(() => {
  if (!isOpen) return
  setTimeout(() => { ... requestAnimationFrame(() => firstFocusable?.focus()) }, 100)
}, [isOpen]) // nested setTimeout + rAF = timing fragility

// Effect 3: Source key sync from selected media attrs
useEffect(() => {
  if (!selectedMedia) return
  const sourceKey = /* 4-way conditional logic */
  setCurrentSourceKey(sourceKey)
}, [selectedMedia, ...]) // can fight with Effect 1

// Effect 4: Initialize media search query from selection
useEffect(() => {
  if (selectedMedia?.attrs?.query) setMediaSearchQuery(...)
  else setMediaSearchQuery('')
}, [selectedMedia?.attrs?.query]) // can reset mid-search

// Effect 5: Upload on unmount (useUploadOnUnmount hook)
// Fires cleanup when isOpen changes - side effect on lifecycle!

1206-line god component with 23+ useState calls across hooks

AIGeneratedImagesPanel.tsx plus its hooks manage: prompt, model, stylePreset, stylePrompt, aspectRatio, count, artStylePreset, artStylePrompt, styleReferenceImages, modelAutoselect, shouldUseThemeColors, isGenerating, hasError, errorMessage, fallbackInfo, lastSearchedQuery, allowRegenerateForEditedImage, scope, entries (upload), isDragging, and more. Each useState is an independent source of truth with no formal coordination.

Two parallel getSelectedMedia implementations

The legacy utils.ts has getSelectedMedia() that wraps the newer selectedMedia.ts version, adding fallback paths for TextSelection, link marks, and NodeSelection. The wrapper adds SmartLayout source defaulting and editType derivation. These two can diverge when one is updated without the other.

// utils.ts - wraps new implementation, adds fallbacks
export const getSelectedMedia = (editor, selection, freshNode) => {
  const selectedMedia = newGetSelectedMedia({ editor, selection, freshNode })
  if (selectedMedia) {
    // adds SmartLayout defaulting, editType, accesoryKeyPath
    return { ...selectedMedia, type: selectedMedia.node.type, ... }
  }
  // Fallback for cases "not handled" by new getSelectedMedia
  if (selection instanceof NodeSelection) { ... }
  if (selection instanceof TextSelection) { ... } // dead code?
}

170-line updateSelectedMedia with 6 responsibilities

A single function handles: (1) fetching fresh node state, (2) position recovery via ID search, (3) attribute merging with Record<string, any>, (4) link mark updates, (5) smart diagram updates, (6) accessory image keypath updates, (7) node type switching, (8) extraction data to positioned textbox conversion, and (9) analytics tracking. No type safety on attrs -- it's Record<string, any> throughout.

Feature flag -> hook nullability -> UI gate pattern

This is the pattern that caused PR #18923. A feature flag controls whether a hook returns data or null. The null return is then used as a truthiness gate to decide which UI to render. When the flag is OFF, the hook returns null, and any component checking that value as a boolean hides its entire UI -- even the parts unrelated to the flag.

// useStyleReferenceUpload.ts -- returns null when flag is OFF
return styleReferenceUploadEnabled
  ? { entries, canAddMore, isDragging, ... }
  : null  // <-- entire object or nothing

// SwitchingArtStyleSection.tsx -- uses it as UI gate
if (showNewArtStyleUI && styleReferenceUpload) {
  return <DeckStyledArtStyleControls .../>
}
// When flag OFF: styleReferenceUpload is null
// -> condition is false -> falls through to legacy UI
// -> deck-styled art style controls DISAPPEAR entirely

Implicit panel registration via flat array

40+ media panels are registered in MediaProviderPanels.ts as a flat array, turned into a Map by .key property. No type contract for what a panel must provide. No validation. Adding a new panel means adding an import to a flat list and hoping the .key doesn't collide.

// MediaProviderPanels.ts
const Panels = [
  BingImagePanel, GiphyPanel, GoogleImagePanel, WebImagePanel,
  LexicaPanel, UnsplashPanel, PexelsPanel, YoutubePanel,
  // ... 30+ more imports ...
  PictographicPanel, PictographicIconsPanel,
]

export const MediaPanelsMap = Object.fromEntries(
  Object.values(Panels).flat().map(panel => [panel.key, panel])
) // no type safety, no collision detection

⚠ Why AI Coding Agents Can't Navigate This

▶

Understanding "Generate" requires 8+ files with no contract

To understand what happens when a user clicks "Generate", an agent must trace through all of these files in sequence:

onClick handler -> useAllowOrUpsell wrapper -> generateImage callback (60 lines) -> getEffectiveStyleConfig -> useImageGenerate.generate() -> 3 API fetch functions -> selectImage callback -> updateAttributes -> updateSelectedMedia (170 lines) -> syncLatestAiImageSettingsToDocAttrs

There is no interface, no type contract, and no documentation connecting these. An agent must read each file, understand the closure variables, and mentally reconstruct the sequence.

Zero unit tests to read for expected behavior

There are zero unit tests for the media drawer, the AI panel, the hooks, or updateSelectedMedia. An AI agent has no spec to reference -- it must infer behavior from implementation. When making changes, there's no way to verify correctness without running the full app in a browser.

Side effects embedded in component lifecycle

Effects are not extractable functions. They live inside useEffect closures with captured variables from component scope. An agent can't reason about "what happens when the user selects media" without understanding React's effect timing, the 5 effects' interaction, and the Redux dispatch cycle.

State derived from multiple sources with undocumented priority

For example, the AI image prompt comes from: (1) user input via useState, (2) currentAttributes.aiParams.prompt, (3) currentAttributes.query (deck-styled mode), (4) auto-enhanced prompt from runEnhanceImagePrompt. The priority rules are scattered across useEffectWhen, useEffect, and the generateImage callback with no single source of truth.

🐛 The Bug That Proved It: PR #18923

▶

How a feature flag silently broke the deck-styled art style UI

1

Feature flag aiStyleReferenceUpload is OFF for some users / environments.

2

useStyleReferenceUpload returns null because the hook checks the flag internally and returns null when disabled. This is the hook's contract: "feature off = nothing".

3

AIGeneratedImagesPanel passes styleReferenceUpload (null) as a prop to SwitchingArtStyleSection.

4

SwitchingArtStyleSection checks if (showNewArtStyleUI && styleReferenceUpload) to decide which UI to show. Since styleReferenceUpload is null, the condition fails.

5

Falls through to legacy ArtStyleControls, which doesn't support the deck-styled presets, the style reference gallery, or the new custom prompt UX. Users see the wrong UI -- not a missing feature, but a complete regression to old behavior.

// The exact line that caused the regression:
// SwitchingArtStyleSection.tsx, line 77
if (showNewArtStyleUI && styleReferenceUpload) {
  return <DeckStyledArtStyleControls .../>  // deck-styled UI
}
// Falls through to:
return (
  <VStack>
    <ArtStyleControls .../>  // legacy grid UI
  </VStack>
) // entire new UI path disappeared

Why no test could have caught it

The visibility decision ("show deck-styled UI or legacy UI?") was entangled with hook nullability, which was entangled with feature flags, which were entangled with component props. Testing this requires rendering the full component tree with all providers, flags, and mock hooks. There's no seam where you could test "given these flags + this state, which UI variant should appear?" as a pure function.

How the visibility function approach prevents it

In the refactored architecture, visibility is a pure function: getArtStyleVisibility(flags, attrs, context) => { showDeckStyledUI: boolean }. The decision doesn't depend on hook return values. You can test every flag combination in a unit test without rendering React. The hook returning null is irrelevant to the UI decision.

    client.refetchQueries({ include: ['GetSavedMedia', ...] })

+ Pros

▶
  • 363 unit tests, zero React dependency for testing. Machines and visibility functions are plain TS. Tests run in <2s with no jsdom.

  • Machine coordination is manual. When aiGeneration needs to tell carousel to update, that wiring is explicit and handwritten.
  • Visibility functions can proliferate. As features grow, the number of boolean fields in visibility objects may balloon.

// Machine definition (XState v5)
const aiGenMachine = createMachine({
  id: 'aiGeneration',
  initial: 'idle',
  states: {
    idle: {
      on: { GENERATE: 'generating' }
    },
    generating: {
      // XState handles the effect natively
      invoke: {
        src: 'generateImage',
        input: ({ event }) => event.config,
        onDone: {
          target: 'complete',
          actions: assign({
            images: ({ event }) => event.output
          })
        },
        onError: 'error'
      }
    },
    complete: { /* ... */ },
    error: { /* ... */ }
  }
})

// In component
const [state, send] = useActor(aiGenMachine)
send({ type: 'GENERATE', config })

+ Pros

▶
  • Built-in devtools and inspector. @statelyai/inspect gives visual state charts, event logs, and time-travel debugging out of the box.
  • Actor model for composition. Parent machines spawn child actors. No manual wiring for cross-machine communication.
  • Parallel and history states. Can model concurrent states (generating + browsing history) natively.
  • Mature ecosystem. Well-documented, large community, TypeScript-first in v5. Googleable patterns.
  • Built-in effect management. invoke/spawn replaces the entire effect bridge pattern. Less boilerplate per effect.
  • Serializable state. Snapshot/restore for SSR, persistence, or debugging.

- Cons

▶
  • ~10kb bundle addition. XState v5 is tree-shakeable but still adds meaningful weight vs zero-dep custom reducers.
  • Opinionated about effects. invoke/spawn couples effect execution into the machine. Harder to swap mock implementations vs the bridge pattern.
  • Learning curve. Actor model, guards, parallel states, invoke semantics: non-trivial for engineers new to XState.
  • Testing requires XState test utilities. @xstate/test or createActor() setup. Not as simple as calling a pure function.
  • Visibility functions still needed. XState doesn't solve the UI conditional derivation problem. You'd still write selectors/derived state.
  • Migration cost. Rewriting 8 machines + wiring. The current tests won't transfer directly.

Migration Effort

▶

Effort: Medium-High -- Rewrite all 8 machines in XState syntax. Rewrite effect bridge as invoke/spawn actors. Rewrite 363 tests to use XState test utilities. Visibility functions can remain mostly unchanged.

Estimated: 2-3 weeks for a senior engineer familiar with XState.

+ Pros

▶
  • Familiar to React developers. Zustand is the most popular React state library. Small API surface, minimal learning curve.
  • Simple mental model. Stores are just objects with methods. No state charts, no transitions, no effect descriptors.
  • Redux DevTools compatible. Time-travel, state diff, action log via browser extension. Zero setup.
  • RSC for data fetching. Credits, history, feature flags fetched server-side. Reduces client JS and waterfall.

  • No state machine formalism. Can't statically verify that "generate" is only callable from "idle". Business rules live in if-statements.
  • AI agents struggle with mutable stores. Harder to reason about state when any action can mutate anything. No declarative state chart to read.

Migration Effort

▶

Effort: High -- RSC requires App Router migration (major lift for entire client, not just media drawer). Zustand store rewrite is medium effort but loses all formal state machine properties. Tests would need complete rewrite.

Estimated: 4-6 weeks including App Router migration. 1-2 weeks for Zustand-only (no RSC).

// Projection builds current state
function projectUI(events: Event[]) {
  return events.reduce((state, e) => {
    switch (e.type) {
      case 'GenerationStarted':
        return { ...state, generating: true }
      case 'GenerationCompleted':
        return { ...state,
          generating: false,
          images: e.images }
    }
  }, INITIAL)

// Time travel = replay events[0..k]

+ Pros

▶
  • Perfect audit trail. Every user action is recorded. Reproduce any bug by replaying the event sequence.
  • Time-travel debugging for free. Undo/redo is just replaying events up to a point. No separate undo stack needed.
  • Excellent testability. Tests are: given these events, assert this projection. Pure function over an array.
  • Multiple projections from same events. UI state, analytics, undo history, and debugging views all derive from the same event log.
  • Natural fit for AI agent comprehension. Agents can read the event log as a sequence of actions and understand the full flow.

- Cons

▶
  • Event schema evolution is hard. Renaming or restructuring events requires migration logic. Old events must still replay correctly.
  • Unfamiliar pattern for React devs. CQRS/ES is common in backend systems but rare in frontend. Steep conceptual learning curve.
  • Projection performance. Replaying all events on every render is O(n). Needs snapshotting optimization for long sessions.
  • Async events are awkward. "GenerationStarted" and "GenerationCompleted" are separate events. The "in-between" state requires careful handling.
  • Overkill for ephemeral UI state. Media drawer state doesn't persist across sessions. The audit trail provides limited real value.
  • Storage overhead. Keeping the full event log in memory for a UI component is wasteful compared to just keeping current state.

Migration Effort

▶

Effort: Medium-High -- The current machines already emit events/effects, so the conceptual bridge is shorter. Main work: define event schema, write projections, handle async event gaps, build snapshotting. Tests translate more naturally since projections are pure reducers.

Estimated: 3-4 weeks. Event schema design is the bottleneck.

Assessment

After analyzing all five approaches across testability, developer experience, migration cost, and architectural fitness for the media drawer domain:

Why the current approach wins

The custom machines approach is the right call for this specific problem. The media drawer is a complex but bounded UI domain. It needs high testability (363 tests prove it), AI agent comprehension (machines are declarative and readable), and zero new dependencies. The effect bridge pattern, while verbose, provides the cleanest testing seam of any approach.

What to steal from the alternatives

From XState: Build a lightweight state inspector / event logger for dev mode. The biggest gap in the current approach is observability. A simple React DevTools panel that shows machine state + recent events would close 80% of the devtools gap at 0% of the bundle cost.

From Event Sourcing: The event log concept pairs naturally with the existing effect descriptors. Consider logging all machine events in dev mode for time-travel debugging without adopting full CQRS.

From Zustand: Nothing structural, but the lesson is valid: if the team finds the custom patterns hard to learn, invest in documentation and worked examples rather than switching to a "familiar" tool that sacrifices testability.

When to reconsider

If Gamma adopts XState broadly across the codebase (not just media drawer), migrating to XState v5 would make sense for consistency. If media drawer panels need independent deployment (unlikely given it's one feature), micro-frontends would become relevant. Neither condition exists today.
