Decision

<img fill> and contain are not supported

Image nodes use regular flow, background, or positioned placement. The supported model has no foreground mode that stretches an image to a complete grid cell.

Removed image states

  • <img fill="true"> does not define a supported foreground cell-fill mode.
  • <img fill="contain"> does not define a supported contain mode.
  • Image nodes do not consume the remaining height of a grid cell.
  • Grid seams do not resize regular image nodes.

Accepted constraints

  • Regular images keep their natural aspect or use an explicit size budget.
  • A photo column does not automatically fill unused cell height.
  • Background images remain out of flow and permit text overlay.
  • Exact panel geometry uses positioned image boxes on fixed cards.

Replacement paths with the supported nodes

Need Supported path Result
An image above or beside text Use a regular <img> in a grid cell. The image stays in flow and keeps its natural aspect.
Uniform image bands Use grid imageAspect and imageShape with regular images. Every direct image child gets the same aspect and shape.
A complete logo, diagram, or screenshot Use a regular image with width and height budgets. The image keeps its natural aspect inside both limits.
Text over an image Use <img background="true"> at the cell or card level. The background covers its container below the text.
An exact full-bleed photo panel Use positionedImageBox on a fixed card. The box owns its width, height, position, and rotation.

Authoring rule

GML authors use only the supported paths above. The renderer report does not present fill or contain as image controls.

  • Do not emit fill="true".
  • Do not emit fill="contain".
  • Use natural aspect or explicit size budgets for in-flow images.
  • Use the background role only for text-over-image surfaces.

Discussion topic

Do we need both card and cell backgrounds?

GML uses one background image role in two parent scopes. The parent determines whether the image covers one cell or the complete card.

Current model: one role, two scopes

Scope GML parent Coverage Text above it Authoring UI
Card background <section> The complete card All card flow content Card style → Background image
Cell background <grid-item> One grid cell Content in that cell No direct control for background="true"

Why card-level support exists

A card background stays independent from the root grid. This separation preserves the content hierarchy when the background covers every root cell.

Semantic ownership

The card owns its background color. The card also owns its background image. The grid owns content layout.

Layout independence

A card-level background sits behind any root layout. It does not add a wrapper cell or change the content hierarchy.

The strongest card-level example: two columns over a full-bleed image

The two-column grid stays the root content with a card background. If the root cell owns the background, it must wrap another grid.

Card-level background

The background and the two-column layout stay as independent siblings. 

<section>
  <img background="true" />
  <grid>
    <grid-item>Left</grid-item>
    <grid-item>Right</grid-item>
  </grid>
</section>
Root-cell background

The background requires a wrapper cell and a nested grid for the same two-column layout. 

<section>
  <grid>
    <grid-item>
      <img background="true" />
      <grid>
        <grid-item>Left</grid-item>
        <grid-item>Right</grid-item>
      </grid>
    </grid-item>
  </grid>
</section>

Consolidation options

Option What it preserves What changes
One role with two parent scopes Full-card surfaces and local text-over-image cells use the same image node and attribute. The editor needs background controls at both container levels.
Card scope only Full-bleed card backgrounds keep the simple root hierarchy. Local background panels need freeform image and text boxes, a nested card, or custom CSS.
Cell scope only Local text-over-image cells stay in the grid model. A full-card background needs a wrapper cell and a nested root grid.
Background data on each container Cards and cells keep both visual scopes through one container API. Media data moves from an image child to section and grid-item attributes.

Questions for the discussion

The main choice is whether local and global background surfaces belong to one role with two scopes.

  • Are local text-over-image cells a core authored composition?
  • Can fixed freeform boxes replace local cell backgrounds?
  • Is a wrapper cell acceptable for every full-card background?
  • Does the UI need the same background control at both scopes?

Image controls

These attrs control the image inside its box. The parent still owns the placement geometry.

Control Storage Renderer behavior
Source src or tempUrl The source resolver selects the display URL.
Crop resize.clipType and resize.clipPath The normal image path requests a cropped image URL.
Width resize.width The value sets the in-flow width in canvas points.
Height budget resize.height The value limits the image and keeps its aspect ratio.
Alignment horizontalAlign The image aligns to the start, center, or end.
Background role background=true The image becomes a cell or card backdrop.
Placeholder showPlaceholder=true The renderer displays the empty media surface.
Upload state uploadStatus The renderer displays status chrome or a spinner.
Generation state loadImageStatus A client slot displays the loading or error state.
Link href and clickBehavior=newTab The renderer wraps the image in a new-tab link.
Lightbox clickBehavior=expand The client supplies the lightbox in read mode.

Behavior notes

These details explain the boundaries between flow images, background images, media variants, and legacy documents.

Grid image bands

imageAspect accepts auto, square, landscape, or portrait.

imageShape accepts square, rounded, or circle. A nested grid does not inherit the parent band.

Card and cell backgrounds

A cell background covers one grid cell. A card background must be a direct child of the card.

Stored flow width and alignment do not size a background image. The parent owns its full-bleed geometry.

Icons and videos

A monochrome icon uses a CSS mask and currentColor. A pictographic icon uses a normal image element.

An uploaded video uses the figure contract. The client supplies VideoSlot. A thumbnail displays the poster.

Crop paths

A normal image sends crop data through the client source resolver and imgproxy.

A positioned image box uses its own geometry. It can also use SVG or safe CSS clipping.

Renderer boundaries

Canvas cards use the new renderer image path. Legacy documents keep the legacy image view.

Grids replace new gallery layouts. Grid marker icons use marker data instead of normal image children.

The client supplies crop controls, resize handles, replacement controls, status UI, and lightbox UI.
